# Design rationale and walkthrough notes
This development record explains the design rationale, significant revisions, walkthroughs and evaluation limits. The assessed report is supplied separately. This record does not contain experimental results.

## Link back to Assignment 1
My Assignment 1 literature review is titled “Overreliance on AI Diagnostic Recommendations in Digital-Twin-Based High-Speed Rail Wheel Production”. It focused on fault candidate selection and independent verification, and drew a clear line between reading an explanation and carrying out physical checks.
This new prototype keeps that separation and logs each action separately. Clicking “acknowledge” in the UI is only a recorded action; it does not prove the operator has understood the information or done a real inspection.

The review also covered mixed outcomes for AI explanations. This prototype does not repeat validation of those papers, and I do not claim to produce new research evidence. There are no participant data, trust scores or real diagnostic accuracy measurements here.

## Applied module concepts
### W01 L02 Ingredients of an Intelligent Interactive System
The lecture slides (pages 5–6, 18, 22) break down sensing, uncertain interpretation, output and human-in-the-loop design, and ask us to identify stubbed/simulated layers.
In this prototype, sensor readings and diagnostic interpretations are simulated. The human loop is implemented: operators can request inspections, change their diagnosis and submit a final decision. There is no real sensor input or adaptive AI model. This simple setup is enough for demonstrating the interaction; agent or multi-agent features are unnecessary for this task.

### W02 L04 Perception, Attention and Feedback
Slides pages 6, 18 talk about attention and the timing of acknowledgement.
I marked anomalies with an amber 3D marker, and also repeat that information in the side evidence panel and station label. Critical evidence is not only shown in the 3D view, so users are not dependent on colour or the model.
Requesting and acknowledging an inspection gives immediate on-screen feedback. Users can pause the rotating wheel, and the interface respects reduced-motion preferences on load. I have not tested whether this improves attention or detection speed.

### W02 L05 Memory, Mental Models and Cognitive Load
Slides pages 8, 10, 17–18 discuss recognition support, reducing unnecessary cognitive load and controlling how much explanation we show at once.
All diagnosis options stay visible, so users do not need to memorise labels. The “Why” panel groups observations, limitations and recommended next checks for each candidate. Inspection results stay on screen after loading.
I also added clear labels stating this is a simulation, to stop users forming the wrong mental model that it connects to live factory sensors. That said, extra written information may still increase reading load, and usability testing would be needed to check this.

### W02 L06 Action, Error, Agency and Decision
Slides pages 9, 14–17 cover constraints, user agency, ranking effects, anchoring and automation bias.
Diagnosis choice and final disposition (hold / escalate / release) are separate choices and start empty. Operators can reject both suggested candidates or change their mind after seeing new inspection evidence.
I removed percentage confidence values from the earlier version. Even so, the first listed candidate may still create anchoring bias.
Guided mode requires both simulated inspection results to be acknowledged before recording a decision. It does not establish that physical checking occurred. Exploratory mode allows users to skip checks and records this behaviour, matching the research aim from Assignment 1.
The two modes cannot demonstrate reduced bias through a simple comparison, because guided mode requires acknowledgement by design.

### W03 L09 Prompting as Interaction
Slides pages 8–10 warn that structured output from an AI can feel convincing, even if it is not correct.
The text inside the “Why” panel is prewritten scenario content stored in src/model.js. It is not generated by a live language model and does not expose model reasoning. There are no API calls or prompt evaluations.
If this system was connected to a real model later, we would need separate checks to validate outputs and evidence coverage, rather than only relying on well-written prompts.

### W04 L10 Context Engineering and Memory
Slides pages 8, 11–12 distinguish saved system state from a human user’s memory.
Case ID, working mode, scenario ID and fixture version are stored so we can track the context of every decision. All logs stay only inside the browser tab and can be exported as JSON.
There is no user profile, persistent model context window or long-term memory. A timestamp in the log does not tell us what the user actually read or understood.

### W04 L11 Retrieval, Grounding and Provenance
Slides pages 8–10 distinguish simply citing evidence from letting users inspect the source evidence themselves.
The “Why” panel lists observations E1–E3 and states which fixture/version this scenario comes from. It also clearly notes that the diagnostic suggestion was not built using independent inspection results.
This applies provenance ideas to static simulated data. It is not RAG, and the text does not make simulated data real.

### W04 L12 Tools, Connectors and the Boundary
Slides pages 5, 8, 13 separate suggested advice, application rules and observed results.
The diagnostic text itself cannot submit a decision. Simple validation rules check that the operator’s input meets the mode requirements. The interface reports the true logged state, including when inspections are incomplete.
There is no tool-calling model, no industrial connector, and no control of real equipment. The “release” button only saves a simulated decision.

## System diagram and information flow
The report's system diagram uses boxes, arrows and short labels to show these flows:

- Simulated fixed observations → scenario state (implemented in code).
- Scenario state → scripted diagnostic suggestions (simulated) and the 3D line view (illustrative geometry).
- Diagnostic suggestions → candidate list and Why interface (implemented).
- Separate simulated inspection data → request and acknowledgement controls (implemented).
- Operator choices and acknowledgements → validation rules → saved decision → read-only summary.
- Interaction events and recorded decisions → in-memory log → JSON export.

The summary displays the saved decision; it does not run another diagnosis. No flow connects a diagnosis to equipment control. Real sensors, trained inference models and factory hardware are outside the developed scope.

## Evaluation and limitations
The current automated suite contains eight state-rule tests and six application-handler tests. Three manual walkthroughs of the updated interface document guided hold, revision after counterevidence and escalation with incomplete verification. Earlier checks covered JSON export, keyboard operation and different screen sizes. The screenshots do not constitute a separate audit of native keyboard focus in the updated interface.
These software tests cannot prove that the interface improves trust calibration, reduces automation bias or is safe for real industry.

A proper future study on explanation effectiveness would need two matched conditions: one with explanations available and one without. That comparison is not built here. Guided vs exploratory mode does not isolate the effect of explanations.
Running the same counterevidence cases repeatedly can create learning effects. Any follow-up user study would need counterbalanced scenario ordering.

Metrics we can collect from logs: how many times “Why” is opened, diagnosis changes, inspection requests, acknowledgements, decisions made without full checks.
Important limits: opening the explanation panel does not mean the user read it; acknowledgement does not mean understanding; duration does not prove engagement; picking the first candidate does not automatically prove automation bias.
I make no claims about real operator behaviour or generalisation to manufacturing settings.

## Significant development changes

The changes below are grouped by feature rather than GitHub upload or commit number.

### Explanation dialog design
I kept the consistent navy industrial theme for panels, and amber remains the distinct colour for anomalies. I do not claim this colour choice improves attention.
The “Why” panel opens as a modal window, so evidence, limitations and suggested next checks sit together in one focused view. Three fixed question buttons are provided; users do not type their own prompts. All responses are pre-written and not generated live. Opening this dialog is logged separately from inspection work.

Trade-off: a modal hides some of the surrounding UI context. It can be closed with Escape, the close button or clicking the background. The native dialog is designed to restore focus to its opening button when closed; the DOM-adapter checks do not verify native focus behaviour. There is also a shortcut to jump to inspection without marking anything as checked.
This design tries to balance controlled explanation length, user agency, provenance and the boundary between advice and action. It is not proven to reduce bias or improve task performance.

### Visual simplification
I put the module name above the project title. Removed redundant banners, extra decorative text and glow effects to reduce visual clutter.
The long disclaimer text inside the modal was removed, but short labels still make it clear this is a simulation and responses are pre-written.
None of the diagnosis or checking rules changed. The goal was to reduce extraneous visual load; I have no usability measurement to show it works better.


### Recorded decision summary
The earlier interface spread the final diagnosis, disposition, checking state and reason across several controls. I added a read-only summary so the final action and its evidence status can be inspected together. It reads the saved decision object, including the diagnosis after any revision, rather than reconstructing it from disabled inputs.

The summary says either “Both inspection results acknowledged” or “Verification incomplete”. It shows requests and acknowledgements as separate counts. Neither label claims that a physical inspection occurred or a diagnosis was proven. The rationale is inserted as plain text. Keyboard focus moves to the summary after recording, and a new case clears the previous summary.

Checks: eight state-rule tests and six application-handler tests passed, as did JavaScript syntax checks. The new tests cover full guided verification, counterevidence revision, zero and partial checks, reset and case changes, and agreement with the exported decision. A DOM adapter cannot validate real focus or layout. Subsequent manual walkthroughs show the recorded summaries for full checking, a revised diagnosis and incomplete verification. These screenshots are distinct from native keyboard-focus or accessibility testing. Scenario fixtures and finalisation rules are unchanged.


### Workflow guide and original logo
I added a compact guide above the workspace: select diagnosis, view explanation, independent checks, and record decision. It describes a suggested route rather than enforcing a new sequence. The active step follows the current case. Viewing Why is optional, and the exploratory route allows recording without acknowledging checks. The guide retains the actual acknowledgement count instead of marking skipped checks complete. A new case also clears the explanation-viewed indication.

The original SVG logo combines a wheel rim, hub, spokes, two rail lines and a small digital node. It replaces the sidebar A↗ and is reused as the favicon. The logo is a static visual identity, not a certification or indication of live equipment integration. No external logo asset or generated bitmap was used.

Fourteen tests now cover eight model rules and six application-handler flows. The additional flow checks optional explanations, guided acknowledgements, exploratory skipping and case reset. The decision summary and model rules remain unchanged. The updated walkthrough screenshots show the guide, logo, optional checks and final summaries. They establish the displayed states in those cases, not comprehensive browser coverage, accessibility compliance or an independent test of native focus behaviour.
